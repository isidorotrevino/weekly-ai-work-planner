# D2.4 — State transitions, integrity and verification

Status: DRAFT v0.4 — 2026-10-17. Extends D2.3; D1 remains approved.

## Decision: transition guards

Allowed edges are seeded by Flyway V4. They are **necessary but not sufficient**: each transition must pass a domain guard inside a DB transaction, write `state_transition_events` and `outbox_events`, and update the entity with `row_version` compare-and-swap. DB trigger enforcement of entity state changes is a further hardening task: V4 seeds the transition graph but does **not** guarantee every SQL UPDATE follows it.

### Task
BACKLOG→READY,BLOCKED,CANCELLED; READY→IN_PROGRESS,BLOCKED,DEFERRED,CANCELLED; BLOCKED→READY,DEFERRED,CANCELLED; DEFERRED→READY,BLOCKED,CANCELLED; IN_PROGRESS→VERIFYING,BLOCKED,FAILED,CANCELLED; VERIFYING→DONE,IN_PROGRESS,FAILED,CANCELLED; FAILED→READY,CANCELLED. DONE/CANCELLED terminal (reopen via explicit new task or future audited exception).

### Operation
READY→LEASED,WAITING_CAPACITY,BLOCKED_APPROVAL,CANCELLED; WAITING_CAPACITY→READY,CANCELLED; BLOCKED_APPROVAL→READY,CANCELLED; LEASED→RUNNING,RECONCILING,CANCELLED; RUNNING→VERIFYING,RECONCILING,FAILED,CANCELLED; VERIFYING→COMPLETED,RETRY_PENDING,FAILED,RECONCILING; RETRY_PENDING→READY,CANCELLED; RECONCILING→VERIFYING,COMPLETED,RETRY_PENDING,FAILED,BLOCKED_APPROVAL; FAILED→RETRY_PENDING (only bounded explicit retry); COMPLETED/CANCELLED terminal.

### Incident
OPEN→TRIAGED; TRIAGED→INVESTIGATING; INVESTIGATING→FIXING,VERIFYING; FIXING→VERIFYING,INVESTIGATING; VERIFYING→RESOLVED,FIXING,INVESTIGATING; RESOLVED→REOPENED; REOPENED→INVESTIGATING. Severity changes are audited separately.

### Capability version
PLANNED→IMPLEMENTED; IMPLEMENTED→VERIFIED,INVALIDATED; VERIFIED→AVAILABLE,INVALIDATED; AVAILABLE→INVALIDATED; INVALIDATED→IMPLEMENTED (requires new evidence). Available requires successful verification for same version/environment; invalidate propagates to dependent tasks and plans.

## Guards and transactional invariants

- Lease claim: lock operation; verify state READY, no live lease, dependencies met, approval, capacity; increment fencing generation; create attempt+lease; append transition+outbox atomically.
- Heartbeat/result: attempt/operation/resource/worker/fencing generation must match; stale results cannot transition state or consume capacity twice.
- On lease expiry, move to RECONCILING; external effects must be inspected before retry. Unknown effect requires approval/escalation.
- Cancellation: request cooperative cancellation first; only terminalize when process and side effects have been reconciled.
- Ledger: budget lock; all allocation references must match budget resource and planning run; reservation cannot exceed available per pool. BORROW is a transfer between pools, not newly created quota. Consumption and reservation are different dimensions; an overrun must be recorded even when it exceeds forecast.
- Superseded plan: new plan immutable after PUBLISHED; existing reservations explicitly transferred/released; never count old and new versions twice.
- DAG: prevent cycles for HARD dependencies and capability-unlock paths in service using a transaction-level lock; soft cycles may be warnings. Cross-project paths can inherit effective priority, never mutate base project priority.

## Migration V4 scope

- Seed allowed transition edges idempotently.
- Add FK-consistent budget binding on allocations, including resource and planning run.
- Add uniqueness for budget window keys and nonnegative lease generations.
- Add indexes for incident triage and allocation lookup.

**Known migration caveat:** existing allocations require a data backfill before enforcing `budget_id NOT NULL`; V4 leaves it nullable and provides `NOT VALID` consistency checks for phased migration. A subsequent migration must backfill and tighten it.

## Integration test plan (JUnit 5 + Spring Boot + Testcontainers PostgreSQL 16+)

1. Flyway clean database: V1→V4; re-run validation; inspect FK, unique, CHECK, partial indexes.
2. Invalid transition rejected in service; allowed transition creates exactly one history event and one outbox event.
3. 20 concurrent claims for one operation: at most one active lease/attempt; stale fencing rejected.
4. Worker crashes after external Git commit before callback: reconciler finds commit; no duplicate commit or second external action.
5. Duplicate callbacks and outbox redelivery: idempotent effects and single ledger correlation key.
6. Two concurrent reservations against the same budget: no negative balance/overbooking; row locks serialize.
7. Unknown quota: cannot be treated as unlimited; budget scheduling returns WAITING_CAPACITY or uses explicit bounded policy.
8. Incident BORROW and RETURN conserve total pool capacity; reservation release does not erase actual consumption.
9. Superseded plan: no double reservation across versions; immutable published snapshots.
10. Capability invalidation blocks hard consumer operations; mockable tasks may continue under contract, but cannot pass final integration verification.
11. Dependency cycle attempt rolls back; cross-project critical-path priority inheritance limited to prerequisite path.
12. SEV1 interrupts only checkpoint-safe operations; noninterruptible work remains fenced and tracked.
13. Approval denial prevents execution; approval expiration forces reevaluation.
14. Source revision conflict with Plane/Drive never silently overwrites manual edits.

## Exit criteria for D2 approval

- Flyway V1–V4 executed successfully on actual PostgreSQL 16+ and tests pass.
- Guards, cycle detection and ledger balance implemented and tested.
- Decide physical capacity ledger model: journal with materialized balances versus balanced accounts. No claim of formal double-entry yet.
- Resolve budget windows relative to actual provider quota-reset windows; distinguish weekly planning horizon.
- Ensure V4 phased FK backfill complete and enforce `NOT NULL` on allocation budget.
- Review DB permissions, immutable history, retention and PII/secrets boundaries.

Until these are met, D2 is design draft, not implementation-approved.
