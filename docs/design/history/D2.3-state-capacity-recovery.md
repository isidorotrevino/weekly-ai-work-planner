# D2.3 — State machines, capacity ledger and recovery

Status: DRAFT v0.3 · 2026-10-17 · Extends D2 v0.2, D1 approved

## Decisions

1. Keep PostgreSQL authoritative for operations, budgets, state changes and audit. Large logs and context packs remain external immutable artifacts with hashes.
2. Weekly allocation defaults: PLANNED 70%, INCIDENT 20%, UNCERTAINTY 10% **per resource**. Quotas for subscriptions are observed/calibrated; no universal token equivalence. A budget with `estimated_capacity IS NULL` cannot be treated as infinite or numerically reserved.
3. Ledger movements are immutable and idempotent via `correlation_key`. `capacity_allocations.consumed_units` is a rebuildable projection, not source of truth.
4. `RESERVE` commits estimated capacity; `CONSUME` records estimate or measured consumption; `RELEASE` returns unused commitments. `ADJUST` records corrections rather than overwriting prior rows. `BORROW` and `RETURN` move a budget between pools, never create subscription quota.
5. Do not sum tokens, percentages and duration into a single physical unit. Keep provider measurements in `capacity_measurements`, and only use a resource-specific calibrated planning unit with a confidence interval. Reconcile quota reset windows independently from calendar weeks.
6. Borrow idle incident reserve only for checkpointable/interruptible planned work; incident work can preempt safely. Uncertainty margin is normally held against overruns, not used as a routine lending pool.

## Transactional capacity invariants

- Lock budget row (`SELECT ... FOR UPDATE`) before reservation, borrowing, consumption, release or adjustment; check all active allocations and movements under the same transaction.
- Reject operations with wrong resource, budget, allocation or attempt ownership. The V3 schema does not yet enforce all these cross-table checks declaratively; implement in service and test concurrent claims.
- Never allow negative available balances. If provider measurements imply an overrun, record the overrun and mark budget `OVERDRAWN` in a later schema revision rather than silently dropping evidence.
- Enforce correlation keys per external effect and replays; append ledger movement and outbox event in one DB transaction.
- Quota measurement may be missing. Store null/unavailable as unknown, not zero. Manual snapshots are provenance-tagged.
- Superseding a published plan creates a new immutable planning run and reconciles open reservations; avoid counting the same physical capacity twice across plan versions.

## State transitions — operational contract

**Task:** `BACKLOG -> READY` when dependencies satisfied; `READY -> IN_PROGRESS` on first operation; `IN_PROGRESS -> VERIFYING` when implementation complete; `VERIFYING -> DONE` when acceptance gates pass. `BLOCKED` and `DEFERRED` are reversible via a new planning run; `FAILED` may be reopened with an explicit event; `CANCELLED` terminal by default.

**Operation:** `READY -> LEASED -> RUNNING -> VERIFYING -> COMPLETED`. `READY -> WAITING_CAPACITY / BLOCKED_APPROVAL`; `LEASED / RUNNING -> RECONCILING` on lease expiry or uncertain external effect; `RECONCILING -> COMPLETED / VERIFYING / RETRY_PENDING / FAILED / BLOCKED_APPROVAL`; `VERIFYING -> RETRY_PENDING / FAILED` on failed gates. `CANCELLED` terminal, after worker termination/rollback is verified.

**Incident:** `OPEN -> TRIAGED -> INVESTIGATING -> FIXING -> VERIFYING -> RESOLVED`; `RESOLVED -> REOPENED -> INVESTIGATING`. Severity can change independently, with audit event and replanning trigger.

**CapabilityVersion:** `PLANNED -> IMPLEMENTED -> VERIFIED -> AVAILABLE`; `VERIFIED / AVAILABLE -> INVALIDATED`. Reavailability requires fresh verification in the target environment and downstream impact analysis.

State transition rules are data-driven in `state_transition_rules` and audit events are append-only in `state_transition_events`. Guard logic belongs to domain services with DB transactions; seed and verify allowed transitions in a later migration. The current V3 table does not automatically prevent arbitrary updates to the entity state columns.

## Lease/recovery protocol

1. Atomically claim eligible operation with `FOR UPDATE SKIP LOCKED`; increment `lease_generation`; create attempt and lease with same generation.
2. Worker heartbeats/renews lease while executing. Every result, checkpoint and renewal carries generation; stale generations rejected.
3. Lease expiration or lost heartbeat causes `RECONCILING`, **not** automatic retry.
4. Reconciler inspects Git commits/worktree, external ticket idempotency keys, and persisted evidence. Outcomes: already applied (recover/verify), not applied (safe retry), unknown (block/escalate).
5. A new attempt gets a new generation and isolated workspace. No simultaneous valid attempts for the same operation.
6. Cancellation requests are cooperative; state becomes `CANCELLED` only after effects/rollback are confirmed.

## Critical D2 follow-ups before approval

- Add seeded, complete transition matrix and tests for illegal transitions.
- Add stronger DB enforcement for budget/allocation/resource consistency and plan version supersession.
- Add worker lease expiration tests, duplicate callbacks, outbox delivery duplicates and reconciliation tests.
- Add budget-window uniqueness/overlap policy and actual quota-reset windows (not just weekly boundaries).
- Decide whether capacity movement needs separate reserved/actual balances and a stronger double-entry account design; V3 is an auditable movement journal, not a formally balanced double-entry ledger.
